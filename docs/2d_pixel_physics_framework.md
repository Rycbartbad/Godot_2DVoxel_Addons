# 2D 像素破坏物理框架（Godot 4 / GDScript）

> 把 Teardown 式的"体素即物理实体"迁移到 2D 像素。本文是设计说明 + 已实现的可运行参考实现。
> 所有性能数字都来自本机实测（Godot 4.7.2 stable 标准版，headless，GDScript），不是估算。
>
> 参考实现位置：`src/` ，自检：`tests/test_core.gd`（35 项）、`tests/test_physics.gd`（27 项）、
> `tests/test_interaction.gd`（41 项）、`tests/test_determinism.gd`（6 项）、`tests/bench.gd`

---

## 1. 一句话架构

```text
输入 / 破坏请求
      │
      ▼
[数据层]  Body ──owns──> Shape ──contains──> PixelChunk (8x8, uint64)
      │                      │
      │                      └─> 贪心矩形分解 ──> 碰撞形状（OBB 集合）
      ▼
[破坏管线]  掩码生成 → 按 chunk 合并 → source & keepMask → 4 邻域连通性 → 分裂成新 Shape/Body
      │
      ▼
[物理层]    IntegrateForces → Broadphase(SAP) → Narrowphase(SAT+裁剪) → Solve(顺序冲量+块求解) → IntegrateTransform → Sleep
      │
      ▼
[渲染层]    每个 Body 一张 RGBA8 贴图，只重建受破坏影响的那些
```

三层职责边界很硬：**破坏只改像素数据，物理只读碰撞形状，渲染只读像素数据**。三者通过 Body 的"脏"标记解耦。

## 2. 为什么 2D 比 3D 简单一个数量级

这是整个迁移方案成立的前提，值得单独列出来：

| 项目 | 3D（Teardown） | 2D（本框架） | 收益 |
|---|---|---|---|
| 自由度 | 6（x,y,z + 四元数） | **3（x,y,θ）** | 状态量减半，积分无四元数 |
| 惯性 | 3×3 张量 + 主轴旋转 | **标量 I** | 有效质量公式退化 |
| 旋转积分 | 四元数 | **θ += ω·dt** | — |
| 连通邻域 | 6（共面） | **4（上下左右）** | 位运算直接做 |
| chunk 存储 | 4×64B 位平面 | **1×uint64** | Godot 的 int 正好 64 位 |
| 接触流形 | 4 点 | **2 点** | 裁剪算法减半 |
| 摩擦切向 | 2 个 | **1 个** | 约束数减半 |
| 宽相 | BVH | **SAP 排序扫描** | 40 行代码 |

**最关键的一条**：2D 的 8×8 chunk = 64 像素 = 恰好一个 64 位整数。整个破坏过程就是几次位运算，没有数组、没有指针追逐。这是 2D 迁移最大的红利。

## 3. 数据层

### 3.1 PixelChunk —— 8×8 像素 = 1 个 uint64

```text
occupancy : int64    bit(x + 8y) == 1 表示该像素实心
material  : byte[64] 下标 y*8+x，0 表示空

位布局（x 是字节内的低位，y 选行）：
    byteIndex = y + 8*z   ← 3D 是这种三段式
    2D 简化成：bit = x + (y << 3)
```

Godot 的 `int` 是 int64 有符号，所以：

- `0x8080808080808080` 这类字面量**超出 int64 上限，不能直接写**，必须用 `1 << 63` 或对掩码取反得到。
- `>>` 是**算术右移**，跨行右移会带符号位，必须 `& 0x00FFFFFFFFFFFFFF` 截断。

框架里把这两个坑都封装在 `pixel_bits.gd` 里了。

### 3.2 4 邻域泛洪 = 几次位运算

```gdscript
static func dilate4(m: int) -> int:
    return m \
        | ((m & _not_col7) << 1) \
        | ((m & _not_col0) >> 1) \
        | (m << 8) \
        | ((m >> 8) & MASK_LOW56)

static func flood(seed: int, occupancy: int) -> int:
    var f := seed & occupancy
    while true:
        var n := dilate4(f) & occupancy
        if n == f:
            break
        f = n
    return f
```

**这就是 2D 相比 3D 最大的实现简化**：3D 里连通分量要开队列跑 BFS，2D 里是纯位运算、无分支、无内存分配。8×8 chunk 最多 64 次迭代，实际 3~8 次收敛。

注意左移要**先屏蔽本行最后一列**（`x=7` 的像素左移会跑到下一行 `x=0`），右移同理屏蔽 `x=0`。

### 3.3 Shape 与 Body

```text
PixelShape  = { local chunk 坐标 -> PixelChunk }
              不变量：内部必须 4 邻域连通，不能有孤岛
PixelBody   = 变换 + 速度 + 质量属性 + Array[PixelShape] + 碰撞矩形
```

- **Shape 的 chunk 坐标是局部的**，这样 Body 旋转时像素数据不用动，只在算世界坐标时套变换。
- **Shape 内部必须连通**是硬性不变量，对应 Teardown 官方那条"只靠棱或角接触的体素不会粘在一起"。分裂后每个连通分量成为一个独立 Shape。
- Body 可以持有多个 Shape（例如一架飞机的机身和机翼），它们之间可以用关节连接（`PWorld.add_hinge / add_slider / add_weld / add_rope / add_spring`）。

## 4. 破坏管线

### 4.1 阶段划分

```text
1. DamageCollect      破坏源（圆 / 线段 / 矩形）
2. ChunkOverlap       按破坏源 AABB 求出受影响的 chunk
3. MaskGeneration     每个目标 chunk 生成 64 位 keep 掩码（bit1 = 保留）
4. ApplyMask          occupancy &= keepMask      ← 一次位与就是一次批量破坏
5. LocalFlood         每个 chunk 内部泛洪得到局部分量
6. SeamUnion          chunk 接缝按位与 → union-find 跨 chunk 归并
7. FastPath           只有一个连通分量 → 直接返回原 Shape（不做任何拷贝）
8. Split              每个存活分量 → 新 Shape
9. Rebuild            重算 AABB / 质量 / 质心 / 惯性 / 碰撞矩形
```

### 4.2 两个必须做对的点

**（a）同一个目标 chunk 只允许一条最终掩码。**
参考实现在 README 里自己把这条列为"未来优化"：它的命令粒度是 `(目标 shape, 目标 chunk, 破坏 chunk)`，一个目标 chunk 被多个破坏 chunk 覆盖时就产生多条 64B 掩码命令，后面再排序合并，造成 `sum(popcount(overlap)) * 64B` 的写放大。
本框架直接在生成阶段就只产出"每个目标 chunk 一条最终 keep 掩码"，从源头避免排序与合并。

**（b）接缝只查 +X / +Y 两个正方向。**

```gdscript
# 水平接缝：A 的第 7 列 与 B 的第 0 列
var common := (c.occ & col7) & ((rc.occ & col0) << 7)
# 垂直接缝：A 的第 7 行 与 B 的第 0 行
var common2 := (c.occ & row7) & ((dc.occ & row0) << 56)
```

只要两次位与就能得到"哪些 y 上有接缝接触"，而且**只写正方向**，天然免锁、可直接并行化。

同理，对角接触天然不算连接（位与根本不会命中），不需要额外判断。

### 4.3 实测：破坏成本

| Shape 尺寸 | 爆炸半径 | 删除像素 | 掩码+应用 | 连通性分裂 |
|---|---|---|---|---|
| 64×64 | 6 | 112 | 0.35 ms | **1.5 ms** |
| 128×128 | 12 | 448 | 0.62 ms | **5.6 ms** |
| 192×192 | 20 | 1264 | 1.42 ms | **14.0 ms** |

> 优化前的数字是 6.2 / 22.5 / 49.5 ms。"单分量快路径 + 去掉逐 chunk 标签数组"这两项带来了 **3.5~4 倍**提升 —— 说明 GDScript 里**分配**往往比算法本身更贵。

## 5. 物理层

### 5.1 管线

```text
IntegrateForces → Broadphase(SAP) → Narrowphase(SAT + 面裁剪) → Solve(顺序冲量) → IntegrateTransform → Sleep
```

固定步长 `1/60` 秒，配累加器（`advance(delta)`），最多补 4 个子步防止死亡螺旋。

### 5.2 质量属性从像素推导（Teardown 的核心机制）

```text
mass    = Σ density(material_i)
com     = Σ density_i * p_i / mass
inertia = Σ density_i * (|p_i - com|² + 1/6)      ← 1×1 方块绕自身中心 = 1/6
```

实现上做了单趟扫描 + 平行轴定理：先累加"绕原点的极惯性矩"，再 `I_com = I_origin - m·|com|²`，省掉第二趟逐像素循环（实测省 35%）。

> ⚠️ 这份质量属性会**推给 Rapier**（op 34 `rb_body_set_density`，推的是平均密度
> `mass / 像素数`）。**不推的话两边质量会静默分叉**：脚本按材质密度算、物理按默认密度 1.0 算，
> 于是所有"按 mass 算力"的地方全错（抓取限力过冲 8.4 倍 -> 一直抽搐）。

**这一条是整个框架里"Teardown 味"最重的部分**：炸掉半面墙，质量自动减半、质心自动偏移、转动惯量自动变化，不需要任何脚本干预。框架已用测试锁定（`mass after damage == 32.0`、`com shifts to x=2`）。

### 5.3 碰撞形状：贪心矩形分解，不是凸包

这是 2D 像素场景下最重要的一个选型：

| | 凸包 | **贪心矩形分解** |
|---|---|---|
| 凹形物体（L 形墙、楼梯、残缺碎块） | 凹角被填平，产生**看不见的碰撞体积** | 精确覆盖 |
| 顶点/形状数 | 不受控 | 实心块退化为 1 个矩形 |
| SAT 分离轴 | 每边一个（可能 20+） | **固定 4 个**（两盒各 2 轴） |
| 面积守恒 | 否 | **是**（矩形面积和 == 像素数，互不重叠） |

实测：16×16 实心块 → 1 个矩形；L 形 → 2 个矩形；爆炸后的残块 → 矩形面积和 == 像素数。

超出矩形预算时会退化成"保留最大的 N-1 个 + 其余并成一个包围盒"，**这是用精度换性能的显式取舍，会在残块上产生少量不可见碰撞**，需要按项目实测调 `max_rects`。

### 5.3b 高速物体：为什么必须"小步走"

离散碰撞有个绕不过去的缺陷：**一步之内的位移超过障碍物厚度时，检测不到碰撞**。
实测（8 像素厚的墙，12×12 的箱子）：

| 速度 | 每步位移 | 修 CCD 前 | 修 CCD 后 |
|---|---|---|---|
| 600 px/s | 10 px | 被挡住 | 被挡住 |
| 1500 px/s | 25 px | 被挡住 | 被挡住 |
| 3000 px/s | 50 px | **穿过去** | 被挡住 |
| 6000 px/s | 100 px | **穿过去** | 被挡住 |

做法是**自适应子步**（`PWorld._compute_substeps`）：按本步最快物体的位移把一步切成 N 个子步，
保证每个子步位移不超过 `ccd_max_motion`。朴素、极稳、结果可复现。

> ⚠️ **两处更正（2026-10）**：
> ① 「也正是 small steps 那一派（Dennis 新引擎）的思路」—— **引用错位**。Dennis 的
>    substepping 是**求解器**子步（Temporal Gauss-Seidel，固定小步数，而且**不重算宽相
>    与接触点** —— Catto 原话："It would be very expensive to recompute the contact points
>    every sub-step"）。这里是**自适应、无上限、每子步重跑整条 Rapier 管线**，正好是
>    他说「非常贵」的那一种。
> ② 「子步上限 `ccd_max_substeps` 兜住性能」—— 它**当时是死声明**（写 16 而无人读，
>    真实钳制是 `ccd_substep_budget = 600`）。现在接回来了，默认 0 = 不限。
>    小碎片那条路径见 `docs/manual/performance.md` 的「小碎片」一节。

**极端情况的实测边界**（1 像素薄墙，12×12 箱子）：

| 速度 | 每步位移 | 结果 |
|---|---|---|
| 1000 px/s | 16.7 px | 挡住（最深嵌入 0.6 px） |
| 5000 px/s | 83.3 px | 挡住（最深嵌入 0.9 px） |
| 20000 px/s | 333 px | 子步顶满 → 需要兜底 |

子步数有上限（`ccd_max_substeps`），顶满之后就回到"能不能穿过去"的问题。
所以还有第二道保险：**位移硬钳** —— 顶满时把每个子步的位移钳在 `ccd_max_motion`，
于是"任何厚度 > ccd_max_motion 的东西都不可能被穿过"成为**无条件保证**，
代价是超高速物体变成慢动作。转角同理（`ccd_max_rotation`）。

> ⚠️ **这道保险只能挂在"子步顶满"这个条件上。**
> 我第一版写成了无条件钳制，结果**所有**物体被限制在每子步 2 像素（=120 px/s），
> 整个游戏变成慢动作：箱子像浮在半空、拖动几乎不动、擦下来的碎块也不掉。
> 一个 bug 同时伪装成三个不相关的故障 —— 安全网一定要挂在它该生效的条件上。

**需要全速前进的东西（子弹、投掷物）走扫掠 CCD**（`PBody.ccd = true`）：
把移动体的 AABB 收成一点、障碍 AABB 按半尺寸膨胀（Minkowski 和），
做一次射线-矩形平板测试取最早命中，命中就把位移截断在表面并消掉法向速度。
这正是 Teardown 的做法：
> 它的 `QueryShot(origin, direction, maxDist, radius)` 是一个**带厚度的射线**
> （半径 = 0.5 就是扫掠球体），子弹这类高速小物体走查询，普通刚体走常规求解。
> 这条分工值得抄：子步化解决"比较快"，扫掠查询解决"极快"。

### 5.4 求解器：顺序冲量 + **2 点块求解器**

基础参数：

| 参数 | 建议值 | 说明 |
|---|---|---|
| 迭代次数 | 10 | 有块求解器后 10 次足够 |
| 恢复系数 | 0.0 | 像素破坏一般不需要弹 |
| 摩擦 | 0.5 | 库仑，按法向累积冲量裁剪 |
| Baumgarte | 0.15 | 速度层位置修正 |
| slop | 0.5 px | 允许穿透 |
| 最大分离速度 | 100 px/s | 防止爆开 |
| 休眠阈值 | 6 px/s, 0.15 rad/s, 持续 0.4 s | 按**岛屿**整体休眠 |

**这里踩过两个真实的坑，值得写下来：**

**坑 1：warm starting 必须用"接触特征 id"匹配，不能用数组下标。**
最初把上一帧的累积冲量按 `[n0,t0,n1,t1]` 存成扁平数组，按顺序回填。问题是接触点的**数量与顺序在两帧之间会变**（1 点 ↔ 2 点），结果上一帧的冲量被搬到错误的接触点上，反而给堆叠注入扭矩。
改成 `(参考边, 入射边, 裁剪序号)` 组成的特征 id 后，匹配不上就自动从 0 开始 —— 这才是 warm starting 的正确形态。

**坑 2：2 点流形必须用块求解器，否则堆叠永远收敛不了。**

实测数据（3 层箱子堆叠 300 帧，起始 x=100）：

| 配置 | 顶层 x | 顶层旋转 |
|---|---|---|
| 10 次迭代，标量求解 | 97.09 | +0.0011 |
| 60 次迭代，标量求解 | 99.65 | +0.0150 |
| **10 次迭代 + 块求解器** | **100.000** | **0.000000** |

标量顺序求解把两个接触点当成独立约束各自迭代，两个点的有效质量互不知情，收敛极慢且残留扭矩；块求解器把 2 个点当成一个 2×2 LCP 一次解出（四种活跃集：双活跃 / 仅点1 / 仅点2 / 双零），**同样的迭代次数下堆叠精度提升几个数量级**。

对像素破坏游戏来说这是不可省的：满地碎块互相堆叠是常态。

### 5.4b 嵌入之后为什么会"粘"在一起：摩擦上限的陷阱

深穿透时如果还用 Baumgarte 在速度层做位置修正，会踩一个很隐蔽的坑：

`max_friction = mu * normal_impulse`，而 `normal_impulse` **包含了位置修正那一份**。
穿透越深 → 修正冲量越大 → 摩擦上限跟着暴涨 → 两个物体被摩擦"焊"在一起，
拉不开也滑不动。

修法是把它拆成**两条通道**（split impulse）：

- **真实速度通道**：`velocity_bias` 只放恢复系数 + 推测接触，不含位置修正。
  于是摩擦上限只反映真实的碰撞响应。
- **伪速度通道**：位置修正写进 `pseudo_linear_velocity` / `pseudo_angular_velocity`，
  只在下一帧的位置积分里生效，不进动能、也不参与摩擦上限。

顺带得到两个好处：深穿透被推开时不会凭空获得动能；嵌入深度也从 10.84 px 降到 ≤1.6 px。

### 5.5 休眠

用并查集按接触关系分岛，**同岛必须一起睡**，否则会出现"下面的箱子睡了、上面的箱子还在它身上"的悬空支撑。

**判据必须是"与尺寸无关"的量。** 现在是 @@物体上最快点的速度 = |v| + |ω| × 包围半径@@，
阈值 @@sleep_linear = sleep_surface = 6 px/s@@，持续 @@sleep_delay = 0.4 s@@。

> ⚠️ 这里曾经是"@@|v| <= 6@@ **且** @@|ω| <= 0.15 rad/s@@"两个绝对量。角速度那条对**小碎块**
> 过于苛刻：6x6 的碎块 @@ω=0.2@@ 时边缘线速度只有 0.6 px/s（肉眼完全静止），却超过 0.15。
> 而岛的计时取**岛内最小值** —— 于是少数几个"吵"的小碎块让**整个大岛**永不入睡。
> 实测 300 碎块场景落定 16.7 秒后，340 个里**还有 335 个醒着**，每帧 92.8 ms 全速空转；
> 改成表面速度后降到 47 个醒着、21.8 ms。见开发日志坑 24。
>
> **推论：多体场景里"能不能睡着"就是它的规模上限。** 判据里任何绝对阈值都会在
> 某个尺寸上失效 —— 绝对角速度对小碎块太苛刻，绝对线速度对大物体太宽松。

**睡着之后要真的"不花钱"。** 睡着体仍需参与碰撞（要被清醒体唤醒），
但它们**不动**，所以一切"对全体无条件重算"的收尾工作都应该跳过：
OBB 缓存、@@swept_aabb@@、@@update_aabb@@、以及宽相里那串属性读取。
（跳过 @@swept_aabb@@ 时要先把它在入睡那一刻**归位到 aabb**，否则留着的膨胀量会让跳过不等价。）

休眠体在求解器里按静态处理（`inv_mass = 0`），并且在窄相收到"清醒且仍在运动"的物体接触时立刻唤醒。这对应 Teardown 的 `IsBodyJointedToStatic` —— 判断"是否还锚定在静态世界"。

### 5.6 实测：物理开销

| 动态刚体数 | 每步耗时 | 流形 / 接触点 | 稳定后仍清醒 |
|---|---|---|---|
| 8 | **0.03 ms** | 0 / 0 | 0 |
| 32 | **1.67 ms** | 15 / 30 | 15 |
| 96 | **22.2 ms** | 113 / 176 | 96 |

**内层成本已经优化过一轮**（见开发日志坑 22），原则是**把迭代不变量全部搬进 @@prepare()@@**：

- 有效质量 k11 / k22 / k12、@@r x normal@@ 的叉乘、逆质量 / 逆惯量、
  切向与摩擦系数 —— 在一次 solve 里都不变，旧写法却在 10 次迭代里各重算一遍；
- 速度采样不再调 @@velocity_at()@@（它内部还会再调一层 @@com_world()@@），
  既然 @@r_a@@ / @@r_b@@ 已缓存，"lv + w x r" 就地写；
- @@collide()@@ 原本把 4 轴 SAT 跑两遍（@@sat_signed()@@ 之后又调 @@sat()@@），
  现在复用前者。

| 指标 | 修前 | 修后 |
|---|---|---|
| 求解阶段（ns / 流形求解） | 8096~11188 | **4809~6706（1.63~1.68x）** |
| @@collide()@@ 每次调用 | 6.282 us | **5.226 us（1.20x）** |
| 整帧（40 箱 + 240 碎块） | 104.2 ms | **82.2 ms（1.27x）** |

> ⚠️ 两处改动都是**逐位等价**的，由 @@tests/dump_state.gd@@（改动前后比对刚体状态到 12 位小数）
> 证明，而不是"测试都过了"。其中 @@collide()@@ 那次一开始漏了一个边界
> （@@sep@@ 恰好为 0 时老代码不生成接触点），dump 立刻打脸 —— 见坑 22。

**结论：GDScript 实现的安全区大约在 30~40 个动态刚体。** 超过之后求解器的方法调用开销主导（每步 10 迭代 × 176 点 × 2 次 `velocity_at` 调用 ≈ 3500 次 GDScript 方法调用）。要上千级碎块必须下沉到 GDExtension（C++），见第 7 节。

## 6. 交互层：绘制 / 擦除 / 拖动

操作映射刻意对齐 Aseprite / Photoshop 的像素编辑器惯例：

| 输入 | 行为 |
|---|---|
| **左键拖动** | 绘制（加像素） |
| **右键拖动** | 擦除（删像素，自动连通性分裂） |
| **中键拖动** | 平移视角 |
| 滚轮 | 缩放 |
| Ctrl + 左键 | 抓取 / 拖动物体 |
| Shift + 左键 | 绘制动态刚体（而不是地形） |
| `[` `]` | 笔刷半径 |
| `X` | 切换材质 |
| `R` / 空格 | 重置 / 暂停物理 |

### 6.1 绘制

规则（@@src/core/pixel_editor.gd@@）：

1. 光标下若命中**动态刚体** → 把像素加进它（"补肉"，质量自动变大）
2. 否则 → 加进该点所在的**静态画布瓦片**（按需创建，64×64）
3. Shift → 本次笔画归属一个新创建的动态刚体

三条规则都不需要特殊处理质量：@@rebuild()@@ 重算体素分布，质量 / 质心 / 惯性 / 碰撞矩形一起更新。实测画 95 个像素后，质量 256 → 351，碰撞矩形从 1 个变成 14 个。

**落笔的方式**：**不补点**，直接按「**像素中心到线段的距离 <= radius**」光栅化整条胶囊
（@@Brush.stroke_circle@@，from == to 时退化成圆盘）。

> ⚠️ 曾经是"沿线按 @@半径/2@@ 补点、每个点盖一个圆盘"，有三个后果（坑 21）：
> ①补点间距被 @@MAX_STEPS@@ 截断后超过直径 → 细笔刷画成**虚线**；
> ②圆盘并集的边缘是**扇形起伏**的 → 同一笔厚度在 38~40 之间波动（"变细"）；
> ③每块瓦片都要把整笔的补点重算一遍 → 白干。
> 换成距离判据后三个问题一起消失，光栅化还快了 **2.2x**。
>
> 另一个坑：@@paint_canvas@@ 的瓦片预算超限时曾经直接 @@return@@，**静默丢弃**笔画后半截
> （实测半径 40、单帧 800 单位的一段只剩 3 像素厚）。现在预算放大到 256，
> 并且丢弃数记在 @@Editor.last_dropped_tiles@@ 里可被断言。

### 6.2 擦除

擦除 = 对区域内每个 Body 施加线段破坏，然后走 @@fracture()@@ 的分裂路径。切下来的部分自动变成动态刚体并坠落 —— 这就是 Teardown 里"打断柱子，上半截砸下来"的最小复现。

**必须注意的度量口径**：@@fracture@@ 会把大部分像素**搬**到碎片 Body 上，那不是"擦掉"。真正被销毁的像素 = 擦前总数 − 原体剩余 − 碎片带走。框架里 @@Editor.erase@@ 返回的 @@removed@@ 就是按这个口径算的（测试锁定：64×16 的墙擦一刀，@@removed == 64@@，而不是 544）。

**碎块闸门**：@@world.enforce_body_budget()@@ 在超过 @@max_dynamic_bodies@@ 时淘汰最小、已休眠、未被抓的碎片。没有这道闸门，连续擦地形几分钟就会积累上千个刚体。

### 6.3 拖动

拖动做成求解器里的一个**速度层约束**（@@src/physics/grab.gd@@），而不是直接把位置设成鼠标位置：

- 抓住物体上的一个**局部锚点**，每帧把它拉向目标点
- 有效质量用 2×2 矩阵求解：@@K = invM·I + invI·[r.y², -r.x·r.y; -r.x·r.y, r.x²]@@
- 位置误差 → 速度偏置，并**限速**避免远距离弹射
- **限力**：约束最多提供 @@max_accel@@ 的加速度，所以重物会滞后、能荡起来，而不是瞬移
- 约束和接触约束**在同一层迭代**，所以拖着物体撞墙时会自然互相制衡，不会穿墙
- 被抓的物体永不入睡

松手即抛出：目标持续移动时松手，物体带走速度（实测 2811 px/s，松手瞬间速度连续，随后继续飞出 453 像素）。**把目标停住再松手不会飞 —— 那是正确的物理，不是 bug。**

### 6.4 一个必须做对的细节：绕质心旋转

刚体绕**质心**旋转，不是绕 Body 原点。@@position@@ 只是形状数据的参考原点：

@@@gdscript
var com_before := b.com_world()
var new_com := com_before + b.linear_velocity * dt
b.rotation += b.angular_velocity * dt
b.position = new_com - b.local_com.rotated(b.rotation)
@@@

画笔绘制出来的物体，原点常常离质心很远（甚至就在世界原点），这条不做对的话物体会绕着一个虚空中的点打转。已加回归测试：形状偏移 500 像素的物体旋转 2.25 rad，质心位移 **0.00000**。

---

### 6.5 "大块像素"：只准缩放相机

**屏幕上方块边长 = `camera.zoom`，仅此一处。** 渲染层不做任何缩放。

逻辑世界（物理、碰撞、破坏、笔刷、质量）永远以体素为单位，渲染也以**同样的**坐标画，
「大像素」纯粹由相机拉近实现 —— 相机是视图变换，不参与任何几何计算，
所以**视觉和碰撞永远一致**。

> ⚠️ **踩过的大坑：曾把缩放加在渲染层**（`node.transform` 的基向量乘上 voxel_world_size）。
> 结果画出来的墙比它的碰撞体大 4 倍：视觉上整栋墙扎进地面，
> 而物理检测报告"只嵌入了 0.6 像素"（那只是 slop）。两边坐标系一分家，
> 后续每个现象都会指向错误的方向。
>
> 相关坑：`Transform2D.scaled()` 会**连原点一起缩放**，
> `Transform2D(rot, pos).scaled(v)` 把物体的世界坐标也乘了 v（实测地面跑到 y=1152，画面全空）。

Demo 里 `-` / `=` 调节方块大小（= 相机缩放），`0` 复位到 3，滚轮在此基础上自由推拉。

## 7. GPU 加速：内核做对了，但当前架构下不划算

### 7.1 已经跑在 GPU 上的部分

渲染：体素数据写进 `ImageTexture` 后由 GPU 放大绘制，采样用最近邻。

### 7.2 破坏内核（compute shader，`src/gpu/destruction.glsl`）

一次 dispatch 完成：破坏掩码应用 → chunk 内 4 邻域连通分量 → 输出分量掩码。

设计上绕了一大圈才走对：

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 每 chunk 64 线程 + 共享内存做标签传播 | 有竞态：空像素渗标签、收敛判定提前 6~7 轮退出 |
| v2 | v1 + 固定 64 轮泛洪（躲竞态） | 正确但**比 CPU 还慢**（barrier 太多） |
| **v3** | **GPU 在 chunk 之间并行，chunk 内部复用 CPU 那套 uint64 位运算泛洪** | **与 CPU 逐位一致** |

v3 的关键洞察：GLSL 没有 uint64，就用 `uvec2` 手写 64 位位运算，
把 CPU 的 `dilate4` / `flood` **原样搬进 shader**。好处是彻底的：
没有共享内存、没有 barrier、没有 atomic → 结构上不可能有竞态，且结果与 CPU 逐位相同。

**正确性验证**（`tests/test_gpu.gd`，12/12 通过）：6 组形状 × (残留占用 · 分片结果) 全部一致，
逐 chunk 比对分量掩码 **0/64 个 chunk 有差异**。

### 7.3 实测：为什么默认还是关掉

| 规模 | CPU | GPU | 提交 / 回读 / 拆包 |
|---|---|---|---|
| 64 chunks | 1.52 ms | —（低于阈值） | — |
| 256 chunks | 6.44 ms | 7.74 ms | 3.84 / 0.48 / 0.01 |
| 576 chunks | 15.59 ms | 15.50 ms | 0.51 / 0.23 / 0.01 |

576 chunks 那次，**GPU 侧只花 0.74 ms**，而整个函数耗时 15.5 ms ——
剩下 14.7 ms 全在 GDScript 的记账上：occ_pairs 组装、材质同步、
`comp_masks` / `node_of` 的 Dictionary 写入、接缝 union-find。

**结论：瓶颈不在 GPU 能加速的那部分。** 把泛洪搬上 GPU 是对的，但周围的数据结构开销没动，
所以总账不亏不赚。真正的出路是把**整条管线**搬进 GDExtension（C++），
而不是只把其中一个内核搬上 GPU。当前 `ENABLED = false`，想验证自己打开。

## 7b. 多线程

原则：**只并行"输出互不相交"的映射**，这样既不需要锁、结果也完全可复现。

### 7b.1 按岛并行求解（`PWorld._parallel_solve`）

约束图里互不相连的"岛"之间没有任何耦合，各自跑完整套迭代拿到的结果与串行**逐位一致**。
这是最安全的一种并行 —— 不需要归约、不需要加锁，连迭代顺序都不影响结果。

实测（16 核，关休眠保证一直有接触）：

| 场景 | 串行 | 并行 | 加速 |
|---|---|---|---|
| 16 堆 × 5（96 动态体, 83 流形, 16 岛） | 10.51 ms | 8.36 ms | **1.26x** |
| 36 堆 × 5（216 动态体, 184 流形, 36 岛） | 23.23 ms | 18.85 ms | **1.23x** |

**修正（后来量出来的）**：上表的 1.2x 有两个原因，其中一个是 bug。

1. **分岛曾经穿过静态体做 union** —— 一整块地面会把压在上面的所有物体焊成一个岛，
   于是岛并行的并行度恒等于 1。同一个文件里的 @@_update_sleep@@ 早就跳过静态体了，
   两处规则不一致。修掉之后（20 塔共用一块地面）从"岛 1"变成"岛 20 / 最大岛占 5%"。
2. **剩下的那个原因才是真的**：没人共享静态体之后，上限仍然受限于
   "最重的那一个岛占总工作量的比例"。

**但更重要的结论是：这条路已经到头了，不要再往"岛内并行"上投入。**
实测（@@tests/bench_parallel.gd@@，交叉重复取最小值）：

| 方案 | 加速 |
|---|---|
| 岛并行（多岛场景） | **1.37~1.64x** |
| 岛并行（单个整块堆，最大岛占 100%） | ~1.00x（**本来就没有并行度**） |
| 全图着色（岛内并行的直接替代品） | 0.90~1.13x（**一律不如岛并行**） |

原因不在分组算法，而在 GDScript 本身：**对象属性读写在多核并发下几乎不可扩展**
（16 线程时单元耗时膨胀 **93 倍**，4 线程只有 4.2 倍，见 @@tests/bench_isolation.gd@@）。
求解器整条热路径都是属性读写，所以**并发拐点大约在 4 个线程**；
再多只会更慢 —— 实测把求解器改成高优先级拿满 16 线程之后，
36 塔场景整步从 14.5 ms 变成 35.3 ms（**0.48x**）。

（注：低优先级通道只给约 30% 的线程，看起来吃亏，实际上正好把并发压在了拐点以下。
这是个"默认值在保护你"的例子，别随手改。嵌套 group task 还会死锁，
见 @@tests/probe_nested_tasks.gd@@。）

### 7b.2 并行连通分量提取（`Destruction._components_cpu`）

每个 chunk 的泛洪完全独立。切成若干段、每段一个任务、**按段序合并** ——
这样 node id 的分配顺序与串行完全一致，结果逐位可复现。

### 7b.3 GDScript 多线程的坑

Godot 的 `Array` / `Packed*Array` 都是**写时复制**，而 lambda 捕获会让引用计数 +1。
理论上子线程里的写入会落到副本上而丢失。实测三种写法（捕获 Array 整体赋值、
捕获 PackedInt64Array 写元素、无锁并发写）**都正常**，但这个边界最好不要赌：
本文的实现统一用 `Mutex` 保护共享写入，只在确实需要的地方开线程。

## 8. Godot 工程化要点

### 8.1 语言选择

**"GDScript 能不能走编译？"** —— 不能，而且原因值得说清：

- GDScript **已经**编译成字节码了，由 C++ 写的 VM 执行；缺的不是编译，是**原生代码生成**。
- Godot 4.x **没有 JIT 也没有 AOT**（给 GDScript 加 AOT 目前只是 open proposal）。
- 导出时的 **binary tokens** 只省**加载时间与体积**，**不改变执行速度**。
- 唯一真正的"编译"路线是 **GDExtension**。

**但编译器本来能替你消掉的那类开销（Variant 装箱 + 堆分配）可以手写掉，而且能量出来。**
实测（@@tests/bench_variant.gd@@）：同一个 SAT 算法，"返回 Dictionary" 2.877 us/次 对
"写类型化字段" 2.510 us/次 —— **13% 是纯粹的装箱税**；而单次"空结果 Dictionary+Array"
分配要 **0.270 us**，在 240 碎块场景里每帧要发生约 13000 次。
把这两处改掉（均逐位等价）之后，@@collide()@@ **7.718 -> 5.695 us（1.36x）**。详见开发日志坑 23。

> **推论**：解释器语言里"装箱 / 分配"本身就是大头 —— 一个**空的 Dictionary** 比一次
> 4 轴 SAT 还值得省。热路径上任何"为返回结果而新建容器"的写法都值得怀疑，
> 尤其是**失败路径上的分配**（那往往是最频繁的一条路径）。

**下一个层级是"数据布局"，但它有一个 GDScript 特有的陷阱。**

把求解器内层从"对象属性"换成 packed 数组（SoA）能拿到实打实的性能
（同进程 A/B：串行 1.25~1.81x；并行天花板 **1.29x -> 1.97x**，因为对象属性的并发争用消失了）：

| 访存形式 | 串行 us/元素 | 16 线程并行 | 并发膨胀 |
|---|---|---|---|
| 对象属性 (AoS) | 1412 | 125017 | **88.5x** |
| PackedFloat64Array | 1493 | **7258** | **5.2x** |

> ⚠️ **但它不是等价变换。** Godot 的 @@Vector2@@ 是 @@real_t@@ = **float32**，
> 而 GDScript 的算术是 float64。对象路径每写一次 Vector2 就舍入一次（一次 @@_apply@@ 舍 3 次），
> SoA 只舍 1 次。而求解器是**带离散分支**的迭代器（LCP 活跃集 / @@maxf@@ 钳制 / @@sep > margin@@），
> 1 个 ULP 改变的是"走哪个分支"—— 结果跳到另一条轨道上。
> 实测：三层堆叠从精确的 100.000 漂到 102.69，单箱落地 300 步后翻倒 90°。
>
> 而且它**不是"更精确的模拟"**：scatter 之后状态照样被舍回 float32，SoA 只是把
> 10 次迭代内部的舍入推迟到子步末尾。见开发日志坑 25。
>
> **结论**：布局收益是真的，但这笔账要在**能显式控制 float32 的地方**结 ——
> 也就是 GDExtension（C++ 里的 @@real_t@@）。留在 GDScript 里就是
> "性能"或"数值等价性"二选一。

**GDExtension 这条路已经实测打通，倍数也量出来了**（同数据、同循环）：

| 场景 | 动态体 | 接触点 | GDScript | C++ | 倍数 |
|---|---|---|---|---|---|
| pile:10:8 | 80 | 150 | 1.766 ms | 0.0220 ms | 80x |
| frag:500 | 500 | 682 | 8.904 ms | 0.0890 ms | 100x |
| **frag:900** | **900** | **2119** | **29.829 ms** | **0.3240 ms** | **92x** |

**负载越高倍数越大**（80x -> 113x）。校验和相对差 3.6e-9，同一套物理。

> 三个要点：
> 1. 不需要 godot-cpp —— 引擎自带 @@--dump-gdextension-interface@@ / @@--dump-extension-api@@，
>    手写 C API 即可（绕开网络、也绕开版本匹配）。
> 2. **MinGW 编的 DLL 能装进 MSVC 编的官方引擎**（实测）。
> 3. **C++ 里算术精度是自己写的** —— 显式用 @@float@@ 就能对齐 @@Vector2@@ 的 float32 语义，
>    于是"堆叠零漂移"那类刀尖性质**有可能保住**，不必重新标定。
>    这是 GDScript 里做不到、GDExtension 里天然可做的一件事。
>
> ⚠️ 但运行时**不扫描** @@.gdextension@@，要手写 @@res://.godot/extension_list.cfg@@
> （静默失败，不报错，见开发日志坑 26）。

你当前的 Godot 是 **标准版（非 .NET）**，所以只有 GDScript 和 GDExtension 两条路：

| 层次 | 建议 |
|---|---|
| 原型 / 玩法逻辑 / 关卡 | GDScript（本框架已验证） |
| 破坏管线 + 求解器（>40 刚体时） | GDExtension C++ |
| 过渡方案 | 先把破坏管线 GDExtension 化（突发、低频、算法清晰），物理留下 |

### 8.2 渲染方案

核心矛盾：破坏是"像素级"的，但 `ImageTexture.update()` 只能**整张上传**。

方案：**渲染单元 = 每个 Body 一张 RGBA8 贴图，尺寸 = 该 Body 的局部 AABB**。

- 静态世界**按 128×128 切成多个 Body**（相邻瓦片形状接触，但静态-静态不生成接触，零开销）。破坏时只重建受影响的那几张。
- 动态碎片本来就小（几十像素），一张贴图足够。
- 建图用 `Image.create_from_data()` 一次性写入 `PackedByteArray`，**不要逐像素 `set_pixel()`**（调用开销差一个数量级）。

项目设置里必须开最近邻采样：
```ini
[rendering]
textures/canvas_textures/default_texture_filter=0
```

### 8.3 其他必须注意的

1. **固定步长**：物理用累加器跑 `1/60`，不要直接吃 `_process(delta)`。
2. **对象池**：Body 是 `RefCounted`，创建便宜，但渲染用的 `Sprite2D`/`ImageTexture` 要复用 —— 破坏时贴图尺寸会变，尺寸没变就 `texture.update()`，变了才重建。
3. **整数像素坐标 vs 浮点物理位置**：物理用 float，渲染时让 Sprite2D 的变换直接跟随，靠最近邻采样自然吸附到像素网格，不要手动 round（会抖动）。
4. **热路径避开 `Array` 装箱**：`for x in 8` 比 `range()` 快；频繁访问的数组用 `PackedInt64Array`/`PackedByteArray`。
5. **`Array` 按引用传递，`Packed*Array` 按值传递**：union-find 的 parent 数组必须用 `Array`，否则每次传参都会拷贝。

## 9. 分阶段实施路线

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **M0** | 像素数据层 + 渲染 | 能画、能在任意位置擦除像素 |
| **M1** | 破坏 + 连通性分裂 | 打穿一根柱子后，上半段掉落（此时可用 AABB 刚体） |
| **M2** | 贪心矩形 + SAT 窄相 | L 形残块不出现悬空碰撞 |
| **M3** | 完整求解器（块求解 + 摩擦 + 休眠） | 3 层堆叠 300 帧零漂移、自动休眠 |
| **M4** | 性能 | 40 刚体 < 3 ms/步；破坏半径 20 的爆炸 < 5 ms |
| **M5** | 交互 | 绘制 / 擦除 / 拖动 / 碎块闸门 |
| **M6** | 扩展 | ~~关节~~（**已做**：铰链/滑轨/焊接/绳/弹簧 + 限位 + 马达 + 断裂）/ 绳索解算 / 载具 / 水 / 火（按玩法取用） |

M0~M5 的代码在本仓库里已经全部可运行，M4 的数字见第 5.6 节。

## 10. 当前实现的边界

> 这张表会随实现变动。**最后核对：本表已反映 CCD / 多线程 / 性能修复之后的实际状态。**

### 10.1 已经做掉的

| 能力 | 状态 | 说明 |
|---|---|---|
| **CCD 连续碰撞** | ✅ | 自适应子步（按最大位移切分）+ 显式扫掠 CCD（`PBody.ccd`）。1 像素薄墙在 **1,000,000 px/s** 下仍挡住。⚠️ 扫掠是 **AABB 级**近似，不是精确 OBB 扫掠 |
| **多线程** | ✅ | ①**按岛并行求解**（约束图不相连 → 无需锁、结果与串行**逐位一致**）实测 **1.37–1.64×**（多岛场景），这是本语言下的上限；②**并行连通分量提取**（切段 + 按段序合并，node id 顺序与串行一致）。⚠️ 加线程是负收益，见 10.2 |
| **抗隧穿/抗粘黏** | ✅ | 推测接触 + split impulse（位置修正走伪速度通道，不进摩擦上限） |
| **子步预算** | ✅ | 子步数按"醒着的动态体数"摊薄，避免一屏碎块把帧时间乘以 16 |
| **僵尸对象回收** | ✅ | `cull_outside()` —— 掉出世界的物体会永远加速并把子步永久顶满 |
| **岛划分正确性** | ✅ | 静态体**不**连接岛（求解器永远不会写它），流形归到动态体所在的岛。修前"一整块地面把全场焊成 1 个岛"，岛并行名存实亡（坑 18） |
| **可复现性** | ✅ | 同配置跑两次**逐位相同** + 长时间不发散 / 不漂移（`tests/test_determinism.gd`，6 项）。⚠️ 原来的「岛并行 == 串行逐位一致」三条断言已随 GDScript 求解路径一起删除 —— 见该测试的文件头 |

### 10.2 仍然是缺的

| 能力 | 状态 | 说明 |
|---|---|---|
| **岛内图着色并行 / 两层混合并行** | ❌ **已评估并否决** | 不是"没做"而是"做了发现不该做"：全图着色 0.90~1.13x（一律不如岛并行 1.37~1.64x）；嵌套任务会死锁；分波写法在最有利场景（最大岛占 92%）下仍是 0.95x。**根因是 GDScript 属性读写在 16 线程下膨胀 93 倍**，并发拐点约 4 线程 —— 在这个语言里加并行度是负收益，先换语言/下沉 GDExtension 才有意义 |
| **GDExtension 下沉** | ❌ | 实测：GPU 内核逐位正确但整体**不快** —— 576 chunks 里 GPU 侧只花 0.74 ms，剩下 14.7 ms 全在 GDScript 记账。真正的出路是把整条管线搬进 C++ |
| 关节（铰链 / 滑动 / 弹簧） | ✅ | 五种（铰链/滑轨/焊接/绳/弹簧）+ 限位 + 马达 + 断裂阈值，求解在 Rapier 的冲量关节里。**破坏时关节转移**仍未做：碎片是新刚体，挂在旧刚体上的关节会随它一起删 |
| 关节岛与 `IsBodyJointedToStatic` | ✅ | `PWorld.is_jointed_to_static(body)` 沿关节图 BFS（直接或间接连到静态世界）；休眠仍交给 Rapier 的岛管理器 |
| 碰撞层 / 掩码 | ✅ | `PBody.collision_layer / collision_mask` -> Rapier `InteractionGroups`（**双向**判据）；查询侧 `Query.require / include`（单向）。**形状级**过滤未做 |
| 关节体（多 Shape 的 Body） | ⚠️ 部分 | 数据结构支持多 Shape，但分裂时按 Shape 独立处理 |
| 全局液体 / 火焰 / 载具 | ⚠️ 部分 | **液体有原语了**：`src/fluid/fluid_pbf.gd` + 原生 `PixelFluid`（PBF 粒子流体，纯视觉、不做碰撞；重力就是一个向量，所以容器转液面就跟着晃）。**火焰 / 载具仍缺**；液体"变成像素参与碰撞"也仍缺 —— 见 `docs/manual/cookbook.md` 第 16 节 |
| 精确 OBB 扫掠 | ⚠️ 部分 | 现在是 Minkowski AABB 近似；精确版需要 rect 级的扫掠 |
| 跨平台确定性 | ❌ | **同平台同构**是可复现的（岛并行逐位一致，堆叠漂移 0.000），但 GDScript 浮点 + 跨平台差异不适合 lockstep 联机 |

### 10.3 已知瑕疵（不影响正确性，但记着）

| 现象 | 原因 | 触发条件 |
|---|---|---|
| ≥3000 px/s 撞墙后**反向弹开** | 位移硬钳让"速度"与"实际位移"脱节，接触求解看到的法向速度远大于真实逼近速度 | 仅当子步预算被摊薄（动态体多）时 |
| 高碎块场景**精度退化为慢动作** | 子步预算摊薄的必然代价 | 这是**刻意选择**：宁可慢动作，不可穿模 |
| 滑过拼接表面时在接缝处**打转**（幽灵碰撞） | 矩形分解的**内部边**被 SAT 当成真面，生成水平法向的推测接触（坑 39） | 地面/平台由多段矩形拼成时；一整块时完全干净 |

### 10.4 性能参考线

| 场景 | 帧时间 |
|---|---|
| 40 箱 + 200 高速碎块 | 8.3 ms |
| 240 碎块 | 7.0 ms |
| 修前（同样的场景） | **513 / 522 ms** |

**瓶颈分解（修正版，@@tests/profile_stages.gd@@，带调用次数）**：

| 阶段 | 占整步 |
|---|---|
| **求解器（SOLVE 总）** | **52~63%**（优化前 62~72%） |

## 11. 陷阱清单（都是实际踩到的）

1. `0x8080808080808080` 超 int64 上限，GDScript 会报错/截断 —— 用 `1 << 63` 构造。
2. `>>` 是算术右移，跨行右移必须 `& 0x00FFFFFFFFFFFFFF`。
3. 左移前要屏蔽本行末列，否则像素会串行。
4. `bit_length()` **不存在**于 GDScript 的 int，最低置位下标要自己按字节+按位两段逼近。
5. 脚本内部不能用自身类名做类型标注（没有 `class_name` 时）—— 用 `get_script().new()`。
6. `var x := someVariantExpr` 推断失败会直接**编译报错**，接触这类表达式要写显式类型。
7. 字典 `.get()` 返回 null 时不能赋给有类型的变量（`var d: Dictionary = dict.get(k)` 会崩）。
8. `Rect2i.intersects()` 没有 `include_borders` 参数（`Rect2` 才有）。
9. 宽相配对必须**按 body id 规范化顺序**，否则 A/B 翻转会让法向翻转、warm start 键失配。
10. 破坏管线里**分配比算法贵**：能省的临时数组一定要省（实测 3~4 倍差距）。
11. 脚本内部**不能引用自身类名**做类型标注或静态工厂（没有 @@class_name@@ 时）—— 把工厂方法挪到调用方脚本。@@get_script().new()@@ 也能用，但可读性差。
12. 交互逻辑不要写进 Demo 脚本：抽成 @@pixel_editor.gd@@ 之后，无头测试能驱动与鼠标完全相同的代码路径。
13. @@Transform2D.scaled()@@ 会连原点一起缩放 —— 给 Sprite2D 加渲染缩放时必须显式构造基向量。
14. **精确覆盖与"矩形数量上限"不可兼得。** 用包围盒给矩形数兜底会凭空造出大量幻影碰撞体
    （实测 2400 像素的梳齿形多出 1600 个碰撞格 + 1260 个重叠格，凹陷形状的碰撞箱完全错掉）。
    现在的策略是 @@decompose()@@ 永远精确，超预算只置 @@budget_exceeded@@ 标志；
    想要近似代理必须显式调 @@decompose_proxy()@@。
15. 关卡地形不要用"第几个瓦片"去推高度 —— 一改瓦片尺寸地面就会整个消失。
16. GPU 泛洪的收敛判定（共享标志 + barrier）在 NVIDIA 上会提前退出。
    要么用结构上不可能有竞态的实现，要么用固定轮数；别赌 barrier 的内存可见性。
17. **画笔横跨多块画布瓦片时，必须把落笔裁剪到每块瓦片自己的范围内。**
    不裁剪等于把整笔画进了每一个重叠瓦片 —— 一笔下去会多出好几份重叠像素和好几个 Body
    （实测半径 6 的一小笔：640 像素 / 4 块，正确值是 160 像素 / 1 块）。
18. **位置修正不能留在速度层。** 它会把摩擦上限撑大，深穿透的物体会被"焊死"（见 5.4b）。
19. **安全网必须挂在它该生效的条件上。** 位移硬钳如果无条件套用，会把整个物理拖成慢动作
    （而且症状会伪装成"物体摆放不对 / 拖动失灵 / 碎块不掉"三个看似无关的问题）。
20. **渲染缩放和物理解算必须共用同一个坐标系。** 把"大像素"做进渲染层，
    会让画面几何和碰撞体差一个倍数，症状千奇百怪（物体扎进地面、笔刷对不上鼠标）。
    正确做法是只缩放相机。
21. **极远坐标**：Godot 的 `Vector2` 是 float32，x=1e6 时分辨率约 0.06 像素。
    实测落地误差 0.514 px（可接受），但再远就会开始丢像素精度 —— 世界尽量贴近原点。
22. **分岛时静态体不构成耦合。** 求解器永远不会写静态体（`_apply` 里 is_static 直接跳过），
    所以"两个动态体都压在同一个地面上"应当分到两个岛。穿过静态体做 union 会让
    **任何带一整块地面的场景退化成 1 个岛**，岛并行静默归零。
    同一个数据结构被两处代码用（休眠分岛 / 并行分岛）时，**两处规则必须一致**。
23. **流形要归到"动态体"所在的岛**，不能固定用 `m.a`。静态地面通常 id 最小，
    结果"所有物体与地面的接触"全挤进地面那一个岛，变成串行瓶颈。
24. **GDScript 的对象属性读写在多核并发下几乎不可扩展**：16 线程时单元耗时膨胀
    **93 倍**，4 线程只有 4.2 倍（`tests/bench_isolation.gd`）。
    推论：并发拐点约 **4 个线程**；并行度不是越多越好，过了拐点加线程就是加耗时。
    测量并行时**必须同时量"每个任务自己的耗时"** —— 只看墙钟会把
    "13.56x 并发 + 17 倍单元膨胀"误读成"并行度很高"。
25. **`WorkerThreadPool` 的低优先级通道只有约 30% 的线程**（项目设置
    `threading/worker_pool/low_priority_thread_ratio`，默认 0.3）。
    `add_group_task(..., high_priority=false, ...)` 实测只用到 4/16 个线程。
    但对**属性读写密集**的负载，拿满 16 线程是负收益（见 24）——
    这里的"吃亏默认值"其实在保护你，改之前先量目标负载，别量合成基准。
26. **嵌套 group task 会死锁**：外层任务数 >= 池线程数时，外层全在等内层，
    而内层永远排不上队。想"外层每岛一个任务 + 最重的岛内层按颜色开子任务"，
    在 Godot 4.7 上直接挂死（`tests/probe_nested_tasks.gd`）。
27. **笔画光栅化按"到线段的距离"判据，不要沿线补点盖圆盘。** 补点的间距是个隐藏参数：
    一旦被上限截断，间距超过笔刷直径就画成**虚线**；即使不截断，圆盘并集的边缘也是
    扇形起伏的（半径 20 时厚度 38~40 波动 = "变细"）。
28. **"把上限调大"只是把触发条件推远，不是消除耦合。** `MAX_STEPS` 从 64 提到 256
    让坑 7 潜伏了很久，直到用户甩一下鼠标就复现（半径 1、单帧 800 单位断 384 列）。
29. **不要静默降级。** `paint_canvas` 的瓦片预算超限时曾经直接 `return`，
    跳过笔画后半截且不留任何痕迹 —— 用户看到的是"笔画断了一截"。
    要么记数（`last_dropped_tiles`）让它可以被断言，要么显式报错。
30. **验证的粒度本身可能对 bug 免疫。** 同一套差集测试在"单次落笔"粒度上完全正确，
    而 bug 全在"每帧一段、多段拼接"里。**测试的粒度要和 bug 所在的粒度一致。**
