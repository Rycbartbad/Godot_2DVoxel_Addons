# 陷阱清单

按「症状 → 原因 → 正确做法」写。**每条都是实际踩过的**，不是理论风险。

---

## 体素层

### 1. lambda 里累积的计数永远是 0

**症状**：传给 `flood` 的 `visit` 明明被调用了，外面的 `count` 还是 0。

**原因**：**GDScript 的 lambda 按值捕获局部变量** —— 改的是副本。

**正确做法**：用引用类型累积。

```gdscript
# ✗
var count := 0
shape.flood(from, Callable(), func(_x, _y, _m, _d):
    count += 1                    # 改的是副本
    return true)

# ✓
var acc := {"n": 0}
shape.flood(from, Callable(), func(_x, _y, _m, _d):
    acc["n"] = int(acc["n"]) + 1
    return true)
```

### 2. 批量写入后脏区域没更新

**症状**：元胞自动机改了体素，但下一 tick 那个区域没被处理。

**原因**：**直改 `chunk.mat/occ/aux` 不会自动标脏**（自动标脏只在 `set_pixel/set_aux/clear_pixel` 这些逐像素路径上）。

**正确做法**：每个 chunk 手动标一次。

```gdscript
c.mat[i] = MAT_ASH
shape.mark_dirty(cx, cy)          # 一个 chunk 一次，不是一像素一次
```

### 3. 脏集合只增不减

**症状**：开了脏区域跟踪，但每 tick 还是处理全部体素，性能没改善。

**原因**：处理完没 `clear_dirty()`，脏集合越滚越大。

**正确做法**：处理完就清，让下一 tick 只看新变化。

```gdscript
for key in shape.dirty_chunks():
    process(key)
    shape.mark_dirty_key(key)     # 本次处理中的改动要重新标上
shape.clear_dirty()               # 但要在标记之后清
```

### 4. 我以为 `set_pixel` 会清掉 `aux`

**其实不会** —— `set_pixel` 刻意不动 `aux`（改材质时通常想保留损伤/引信）。
会清 `aux` 的是 `clear_pixel` 和破坏路径（像素没了，历史也没意义了）。

**所以如果你看到损伤消失，是在别的地方被 `clear_pixel` 或 `apply_keep_mask` 清掉的。**

### 5. 逐像素 `set_pixel` 慢到不可用

**症状**：几千个像素的编辑吃掉好几毫秒。

**原因**：1289 ns/像素（含 chunk 查找+创建+标脏，多层函数调用）。

**正确做法**：走批量路径，527 ns/像素。见 performance.md。

### 6. 热循环里调 `neighbors()` 分配了一堆数组

**原因**：`neighbors()` 每次调用都新建 `Array`。

**正确做法**：直接内联 `PixelShape.OFFSETS_4` / `OFFSETS_8`。

## 坐标空间

### 7. 破坏打在了错误的位置

**症状**：挖洞的位置偏了，或者偏得离谱（尤其物体旋转过之后）。

**原因**：**`Destruction.Damage` 的坐标是形状局部像素空间**，不是世界空间。

**正确做法**：用 `PixelPhysics.carve_circle/carve_rect/cut` 那一组（收世界坐标，内部换算）。
非要直接用 `Damage` 的话，自己 `body.to_local(world_point)`。

### 8. 形状没有自己的局部变换

**原因**：像素直接活在**刚体局部**空间里，形状不带独立变换。

**正确做法**：`shape.get_pixel(x, y)` 的 `(x, y)` 就是刚体局部坐标取整；
换世界坐标用 `body.to_world()`。

### 9. `add_ground` 的地面位置不对

**原因**：`rect.position` 是**左上角**，不是中心。

**正确做法**：`Rect2(-800, 300, 1600, 60)` 表示从 `(-800, 300)` 开始、宽 1600 高 60。

## 事件

### 10. 接触事件一条都没有

**原因**：**默认关闭**（对象分配在 GDScript 里不便宜）。

**正确做法**：`px.world.contact_events_enabled = true`。

### 11. 同一次撞击触发了两次

**原因**：有子步时，**同一个配对可能在一步里出现多次**（每个子步一次），引擎不跨子步去重。

**正确做法**：要「每步一次」就按 `c.is_new` 过滤。

### 12. 旋转物体的撞击检测不到

**原因**：如果自己拿 `linear_velocity` 算接近速度，会漏掉转动贡献。

**正确做法**：`c.approach` 已经是**接触点处**的速度（含转动）—— 实测一个旋转长条
质心几乎不动，但边缘接近速度是 156 px/s。别自己算。

## 参数耦合（改之前必须知道）

### 13. 改了 `max_speculative_margin` 之后薄物体开始穿模

**原因**：它必须 **< `ccd_max_motion`**（默认 1.5 < 2.0）。

### 14. 改了 `sleep_surface` 之后静置场景睡不着

**原因**：它曾经**和接触点公式绑死**（`sleep_surface = 6.0` 是按当时的公式调的）。

> 这条有惨痛背景：修 `support()` 返回角点而非最近点的 bug 时，
> 把接触点公式「改正确」反而让 `sleep_box` 从 12/12 掉到 10/12、
> `test_parallel` 里方块下沉 5250 像素。最后两条路径统一回原公式才恢复。
>
> **后续（已解决）**：真正的问题不是"哪个公式"，而是**合成接触点**这个做法本身 ——
> 它把点放在切向重叠区间的中心，而地面比箱子宽得多时，那个中心恒等于**箱子自己的
> 形心**，于是角接触的力臂恒为 0，法向冲量穿心而过，方块被托在自己的重心上、
> 40° 也永远不倒（表现为"角接触不产生倾倒力矩"）。
> 现在分离与穿透走**同一套**参考面/入射面裁剪，接触点就是真实几何。
> 实测 `sleep_surface = 6.0` 已经够用（4.0 才不够），12.0 偏松。
> 详见 `collide.gd` 里那段墓碑注释与开发日志坑 38。

### 15. 改子步数之后物理结果变了

**原因**：子步数会改变接触时序，进而改变结果。而且它和 speculative margin 耦合。

**正确做法**：别手调，让自动子步决定。

## 模块与资源

### 16. 报错说「类型 pbody.gd 赋值给类型 pbody.gd」

**原因**：addon 里的脚本和 `src/` 里的是**两份不同的资源**。
addon 代码里用 `res://src/...` 做类型标注就会撞上这个。

**正确做法**：addon 里的脚本互相引用必须用 addon 路径（构建脚本负责改写）。

### 17. 退出时报 resources still in use at exit

**原因**：模块级的静态注册表持有着刚体引用。

**正确做法**：现在 `PWorld._init()` 自己登记、`NOTIFICATION_PREDELETE` 自己注销 ✓。
自己写新的模块级注册表时请照这个模式 —— **让拥有者负责生命周期**，
调用方就没有「记得注销」这件事。

### 18. 从 C++ 里 resize PackedByteArray 崩溃

**原因**：GDExtension 的 `ptrcall` 路径下，调用方给的模板缓冲是只读的。

**正确做法**：**调用方准备缓冲并给足容量，C++ 只往里写**。
容量不够时 C++ 返回「正好写满 cap 条」，GDScript 侧靠这个信号检测并扩容重试。

## 数字与格式

### 19. `%.12e` 报错

**原因**：GDScript 的 `%` 格式化**不支持 `%e` / `%g`**。

**正确做法**：用 `%.12f`，配合足够的宽度。

### 20. `Vector2` 和 GDScript 标量的精度不一致

**原因**：Godot 的 `Vector2` / `Rect2` 是 `real_t` = **float32**；
GDScript 标量是 float64。`Vector2 * real_t` 会**先把标量截成 float32 再乘**。

**正确做法**：移植/重写引擎代码前读 `addons/pixel_destruction/docs/PRECISION.md`。
这不是理论风险 —— 求解器做到逐位一致就是靠把这些规则一条条对齐的。

## 材质

### 21. 材质 0 的像素看不见

**原因**：**材质 0 = 空**。像素的占用由 `occ` 位掩码决定，材质 id 从 1 开始。

**正确做法**：自定义材质从 1 开始编号。

### 22. 把损伤编码进了材质 id 的高位

**原因**：那会污染材质表，而且切分/复制/blit 时极易丢。

**正确做法**：用 `aux` —— 引擎不解释它的语义，只保证它跟 `mat` 一起被复制、切分、保留。

## 23. 别指望用 GDScript.reload() 检查手册里的代码块

**症状**：想给「手册里的样例能不能跑」做一道闸门，写了脚本把 markdown 的
代码块抽出来、包进 func、用 GDScript.new() + set_source_code() + reload() 编译。
结果 **20 个块里 19 个报失败**，但它们是**完全合法**的用法示例。

**原因**：reload() 做的是**完整编译**，不是只解析 —— 片段里引用的 px / body /
shape 都没定义就报错。而这些名字的上下文在**正文**里，不在代码块里。
给它补一段合成前导（声明 px / body / shape ...）也没用：片段用到的名字是**开放的**，
补不全。

**正确做法**：要让这种检查成立，样例必须**自包含** ——
把每个样例写成 tests/manual_samples/ 下一个**真的能独立运行**的文件，
然后用一个脚本把它们挨个 run 一遍。那样检查的是「样例真的跑得起来」，
比「解析得过」强得多，而且不会误报。

**留在这里的教训**：会误报的闸门**比没有闸门更糟** —— 它会训练人绕过它，
那这条规则就死了。check_docs.py 上也踩过一次（见 tools/check_docs.py 里的注释）。
工具留在 tools/diag/compile_manual_blocks.gd，仅供人工排查，**不要接进 CI**。
