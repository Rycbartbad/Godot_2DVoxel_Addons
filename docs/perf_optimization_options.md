# 性能优化方案清单（实测账 + 排序）

> ⚠️ 这份清单只写**量过的**东西。本会话每一次凭直觉归因都错了 ——
> 以为是质量扫描（其实是同一个函数被调了两遍）、以为是内存分配（其实摊在十来个
> 小操作上）、以为 touches_boundary 是热点（其实只有 0.065 ms）。
> 所以每条都带"依据"；没量过的一律标注出来，不写成结论。

## 一、现状账（768x100 地面，干净口径）

| 场景 | 实测 |
|---|---|
| 内部小洞 r=4（不跑连通性判定） | **1.92 ms/笔** |
| 贴边界小洞 r=4 | **6.65 ms/笔** |
| 沿边界拖一笔 90px | **8.36 ms/笔** |
| 大半径切一刀 r=60（**第一次**，生成碎片） | **31.07 ms** |
| 同上后续（作用在已经裂开的碎片上） | **14.43 ms/笔** |

第一次切一刀的完整账（`world.fracture` 实测 ~36 ms，抖动 ±15%）：

    apply_damage            5.9
    split                  13.5   ├ _assemble 的逐块拷贝 7.7   <- 最大项
                                  ├ _group（并查集）      3.8
                                  └ _components_cpu       2.0
    两片 decompose          6.3
    MassProps               5.1   （真实路径只付碎片的 ~2.5）
    其余                    ~6

**规律**：所有热点的量级都是 **每 chunk 0.3~7 us、每像素 ~0.5 us** —— 全是 GDScript
解释器开销。所以只有两条路能"大幅"提升：**让一次操作覆盖更多数据**，
或者**别用 GDScript 跑**。

## 三、待做（按 收益 x 风险 排序）

### 方案 A：把五个内核搬到原生代码（**10~100 倍**，最大的一档）

| 内核 | 现状 | 实测 |
|---|---|---|
| `make_keep_mask`（伤害命中判定） | 逐像素 | 5.9 ms / 14400 像素 |
| `MassProps.compute` | 逐像素（已改逐块 popcount，7 倍） | 5.1 ms |
| `_assemble` 的逐块拷贝 | 逐 chunk | 7.7 ms / 1098 chunk |
| `_group` 并查集 | 逐 chunk | 3.8 ms / 1248 chunk |
| `_decompose_block` 网格构建 | 逐 chunk 行 | ~0.5 ms/块 |

依据：这些在 Rust 里都是**几十微秒**级别（同样的 1248 个 chunk）。项目已经有通道：
`RapierPhys.cmd(in, out_template)` + `tools/build_addon.py`，而且数据本来就是位掩码
（chunk 的 64 位 occ + 材质表），传给原生几乎零转换。
⚠️ 代价：addon 不在仓库里（`check_addon.py` 退出 1 是正常态），构建链要跟着走；
"纯 GDScript、零依赖"这个卖点会打折。
⚠️ 未量：搬过去之后的真实端到端收益（我按每操作成本外推，没有实测）。

### 方案 B：split 三趟合一 + 按块缓存连通分量（**1.5~2 倍**，纯 GDScript，风险最低）

现在一次破坏要**反复整形状扫描**：`_components_cpu`(1248) -> `_group`(1248) ->
`_assemble`(1098) -> `_block_rects`(1248 发现 + 12x64 指纹) -> `MassProps`(碎片 549)。
按块缓存**连通分量**（和现有按块矩形缓存同一个模式：自校验指纹 + 只重算变了的块）
能拿掉 `_components_cpu` + `_group` 的 ~5.8 ms。

⚠️ **修正**：我先前说这条是"5~10 倍"是**错的**。split 的 13.5 里有 7.7 是**逐块拷贝**，
而拷贝由数据模型决定（分片必须拥有自己的 chunk 数据），缓存动不了它。
真实预期是 13.5 -> ~8 ms（1.5~2 倍）。

### 方案 C：拷贝的数据模型（分片与母体共享 chunk，写时复制）

拷贝是 split 里最大的一项（7.7 ms / 1098 chunk）。让分片**共享**母体的 chunk 对象
（COW 语义）能把它降到接近 0。⚠️ 风险高：chunk 的 `occ` 是 int（不是 COW），
两边共享会让一方的破坏改到另一方 —— 需要给 chunk 加"共享"标记并在写入前分离，
这是**数据模型级**的改动，且分片与母体的生命周期不重叠这一点必须论证清楚。
⚠️ 未量。

### 方案 D：Rapier 侧

- **碰撞体数量**：修掉分片重复之后每片 380 -> 53 个矩形（少了 7 倍），实心区域靠
  最大行程合并回到 1 个矩形。远处/静止物体可以用更粗的块（128）继续减。
  ⚠️ 未量：矩形数对 step 时间的实际影响。
- 子步数与 warm-start 策略：项目里已有相关逻辑和调优记录（见 pworld 的注释）。

### 方案 E：GPU 路径只覆盖一半

`apply_damage_and_split_gpu` 用 compute shader 一次 dispatch 同时做"破坏 + 分量标注"，
但**只在有 RenderingDevice 时启用**，而 `_assemble`/`_group`/decompose/MassProps 仍是 CPU。
⚠️ 本清单所有数字都是 `--headless` 的 **CPU 回退路径** —— 有 GPU 的机器上
瓶颈分布可能不同（伤害那段可能已经在 GPU 上），但"生成新实体"那一段**无论如何都是 CPU**。

### 方案 F：并行化

`_components_cpu` 已经用 WorkerThreadPool（13 线程，1.9 ms）—— 收益有限，
因为共享的 Dictionary 写入要串行化，而 GDScript 的小操作本身太贵。
可试：把"多个受影响 body 的破坏"合成一个 group task。⚠️ 未量。

## 四、已经排除的（别再试）

- ❌ **"编辑器笔画插值成多段，可以合并"**：前提不存在。`Editor.erase` 本来就把
  整笔变成一个 `Damage.segment`，只调**一次** `fracture`。我一度把它写成方案，
  量了才发现是错的 —— 真正的原因是局部连通判据的探测框上限太小（见方案 F/已完成表）。
- ❌ **继续在 GDScript 里微调**：已经贴着解释器地板（"零拷贝共享"只拿到 0.9 ms）。
- ❌ **用脏标记做缓存失效**：项目在这条路上栽过多次，一律用自校验指纹。

## 五、方法论（比任何单个优化都值钱）

1. **先量账，再动手。** 本会话每一次凭直觉归因都错，每次都是量一遍才找到真凶。
   探针留成常驻的：`profile_sync.gd`、`profile_split.gd`、
   `bench_erase_big.gd`、`bench_erase_boundary.gd`。
2. **闸门要覆盖基准覆盖不到的路。** 8 条基准逐位不变会给人**虚假的安心**：
   我自己引入的"分片碰撞体重叠"（每片 380 个矩形、每个像素被覆盖 2 次）就是靠它漏过去的
   —— 基准不走 split。补了 `validation_fragment_cover.gd`。
3. **位等价优先。** 能做位等价的改动（内联、去重、快路径）就配逐位对拍的闸门
   （keep mask 12000 组、网格缓存 111 组）；做不了位等价的数值重排（质量快路径）
   就配**冻结旧实现**的差分闸门 + 1e-12 相对误差，并让 8 条基准当最终判据。
4. **提交后核对工作区。** 我有一次把修复改在 `destruction.gd` 却只提交了
   `greedy_rects.gd` —— 闸门是绿的，因为它跑的是工作区。现在提交后一律
   `git status` 确认，并且**看懂**那个 `M` 是谁的。
