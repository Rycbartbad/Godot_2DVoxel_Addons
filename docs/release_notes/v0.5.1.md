# v0.5.1 —— 碰撞体斜边"取中间"（不再完全包裹）

## 一句话

v0.5.0 的拟合是**保守包裹**（碰撞体一定把像素整个包住）；这一版把**拟合出来的斜边**
往里挪**半个像素** —— 斜边穿过锯齿的中线：**台阶尖露在碰撞体外面、凹口被碰撞体盖住**。

⚠️ **本版改了原生 DLL**（`fastphys.dll` + `rapier_bridge.dll`），消费方必须重新部署 addon。

⚠️ **轴对齐的边一个字都没动** —— 它们是真实的像素边界。所以：

- **实心块（矩形）的碰撞体与 v0.5.0 逐位相同**；
- **8 条逐位基准全部不变**（基准场景全是实心块 —— 这也是一条反向证据：
  这个改动只影响"拟合出来的边"）。

---

## 实测（40 级锯齿楼梯）

| | 完全包裹（v0.5.0） | **取中间（本版）** |
| --- | --- | --- |
| 顶点 | `(0,0) (40,0) (40,1) (1,40) (0,40)` | `(0,0) (40,0) (40,0.293) (0.293,40) (0,40)` |
| 偏离 | 0.49 px（全在一侧） | **0.208 px**（两侧） |
| 面积 | 839.5（> 像素 820） | **811.7**（< 像素 820） |

最后一行是这次改动最该记住的事：**"碰撞体面积 >= 像素面积"不再成立**。
拟合现在是**双向有损**的（凹口处比像素大、台阶尖处比像素小），两个方向都受
`poly_dev_tol` 约束；`Result.max_deviation` 取绝对值，所以"削掉了多少"也会被报出来。

## 挪多少

- 半个像素（像素量化下锯齿深度就是 1 像素左右，半个像素就是中线）；
- 上限：**不许把薄片削没** —— 最多挪最小宽度的 1/4（薄片最多掉一半厚度）；
- 削太狠（面积掉一半以上）就退回不挪 —— 宁可"包住"，也不要一个不存在的碰撞体。

## 闸门

`tests/validation_poly.gd` 从 16 条扩到 **18 条**，两条新断言直接量甲方要的东西
（**按面积采样**，不是只问像素中心 —— 挪半像素之后，锯齿上的像素中心正好落在
碰撞体的边上，那正是"取中间"的定义）：

- 「斜边是**居中**的：有像素面积露在碰撞体外面」（0.25 像素采样，120 个点）；
- 「斜边是**居中**的：也有碰撞体盖在没有像素的地方（凹口）」（39 个点）。

覆盖判据从"像素必须在多边形里"改成**双向容差**；凸性判定加了 1e-6 数值容差
（挪边产生的交点会与邻居几乎共线，叉积 ~1e-9，不是反例）。

全部 22 个 `test_*` + `validation_*` 全绿，原生与 GDScript 参照实现**逐位相同**。

## 踩到的坑（写进 pitfalls 28 了）

法线取 `(-e.y, e.x)`，长度 = **边长**（那条斜边 55 像素）—— `a + nrm * 0.5` 实际挪了
**27 像素**，多边形被削没，然后"削太狠就退回不挪"的兜底**静默**返回原多边形：
端到端看起来就是"这个函数没生效"。

> **兜底要能说话。** 退回原状是安全的默认值，但它会把"算错了"伪装成"没生效"。

## 消费方要做什么

1. 重新部署 addon（DLL 与 GDScript 都变了）。
2. 若你写过"碰撞体面积 >= 像素面积"这类断言，改成双向判据。
3. 想要逐像素精确（老行为）：`world.poly_colliders = false`。
