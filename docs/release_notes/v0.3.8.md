# v0.3.8 —— 分片组装整块搬对象（破坏再快 24%）+ 扁平化的实测结论

## 一句话

分片组装不再逐块分配 + 拷贝：破坏路径（`fracture` / `detach` / `fracture_pixels` /
`ensure_connected`）都是"用分片替换母形状"的语义，所以整块可以**直接搬 PixelChunk 对象**。
**768x100 一刀两半：30.9 -> 23.6 ms（-24%）**。

同时把"扁平化 shape 数据"这一步**先量了一遍**：GDScript 形态是 **0 收益**（已回退），
结论与后续路线写在 development_log。

## 实测（tests/diag_split_profile.gd）

| 场景 | v0.3.7 | v0.3.8 |
|---|---|---|
| 端到端 `fracture`（768x100 一刀两半）| 30.9 ms | **23.6 ms** |
| 端到端 `fracture`（200x200）| 19.4 ms | **17.2 ms** |
| `detach`（768x100）| 11.7 ms | 11.6 ms（它的 split 落在小形状上）|

## 新增 / 改动

| 接口 | 说明 |
|---|---|
| `Destruction.split(shape, min_pixels, adopt := false)` | `adopt=true` = 调用方**保证母形状会被丢掉**，整块拷贝直接搬对象（不分配、不拷表）。判据是 `mask == src_chunk.occ`（不是 `mask == -1`：占用不满的块只要"本分片拿走了它的全部像素"，搬对象同样精确）|

> ⚠️ `adopt` 是**所有权转移的声明**，不是优化开关：传 `true` 之后母形状不能再被使用。
> `ShapeOps.split` 那条公开路径**必须传 false**（它要保留母形状的残余内容）。
> ⚠️ 逐块 `mark_dirty_key` **故意保留**（1.27 ms / 1248 块）：那是给游戏层 `take_dirty_keys`
> 用的，省掉它会变成静默的行为变化。

## 扁平化：先量再决定（本版**没有**改数据布局）

按"最小可验证的一步"做了有序块表 + 自校验索引（连通分量按下标跑、邻居查找每块 6 次字典 -> 2 次）：
**67 个闸门全绿，但实测 0 收益** —— `_group` 5.15 -> 5.17 ms、端到端 23.6 -> 23.7 ms。
原因是**瓶颈在解释器每轮的固定开销，不是字典查找**（与"接缝循环里 `has()+[]` 改 `get()`
反而慢 9%"那条独立测量一致）。按本仓库的规矩（没有实测收益的复杂度不留）**已回退**。

修正后的结论：剩下的 ~15 ms（连通分量 6.2 + 质量属性 ~9）**只有搬进原生才拿得到**，
而它要求：① 数据扁平（会**破坏 `c.mat[i] = v` 惯用法** -> `mat`/`aux` 改成方法访问，
消费方要跟着改）；② 三个原生 op + 一条"新旧逐位一致"闸门；③ 重编 DLL + 重跑基准。
**收益上界约 23.6 -> 12 ms/次，代价是消费方改代码 —— 要不要走这一步等决定。**

  需要树内 addon 构建：25/25、14/14）；
- 诊断 `tests/diag_split_profile.gd` 现在**同时量**默认路径与 adopt 路径。
