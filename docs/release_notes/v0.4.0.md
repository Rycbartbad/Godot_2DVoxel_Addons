# v0.4.0 —— PBF 粒子流体 + 连通分量标注原生化

## 一句话

两件事：**纯视觉的粒子流体**（原生 `PixelFluid`）和**连通分量标注原生化**
（`PixelRaster` op 3）。前者让"瓶子里的液体跟着容器转"变成一次 `step`，
后者把 CA / 游戏层最常问的那个问题（"哪些体素属于同一个连通体"）从 6.05 ms 降到 1.91 ms。

⚠️ 本版**改了原生 DLL**（新增 `PixelFluid` 类、`PixelRaster` 多一个 `components` 方法）——
消费方必须重新部署 addon。没部署也不会算错：两条路都**逐位相同**，
拿不到扩展就 `push_warning` 后退回 GDScript 参照实现（慢，但结果一样）。

## 一、PBF 粒子流体（`src/fluid/fluid_pbf.gd` / 原生 `PixelFluid`）

### 它是什么

纯**表现层**的液体：不参与物理像素、不做碰撞、不进 `collect_shapes()`。
用途是"容器转动时液面跟着变"这类效果。参数取自
PinkiePie1/CH32V203Dev 的 `Apps/fluid_vb/SandSim.c`（同一套参数在 144 MHz、
**无 FPU** 的 RISC-V 上跑过），算法是 Matthias Müller 的 PBF。

### 为什么是粒子而不是格子流体

PBF 里**没有"下"这个概念** —— 重力只是一个加速度向量，加到粒子速度上；
转动 = 换一个向量，没了。而格子流体每一步都要判断"哪个邻居算下坡"，
45 度时液面变平变慢、斜对角流的权重惩罚、perp 用 `1-|cos|` 近似……
所有角度相关的怪味都是从那个判断里长出来的。

### 坐标与单位（踩过坑的地方）

粒子活在**自己的域**里（`[0, nx*spacing] x [0, ny*spacing]`），不是世界像素；
重力也在这个域的单位里，按"域有多高"换算（`gravity_px * spacing`）。
调用方负责把域映射到目标区域 —— 这条隔离让"瓶子 51x27 像素"和"LED 矩阵 17x18"
能用同一个内核。

### 性能

实测（`tests/bench_fluid.gd`，两边同一份数据、各 20 步预热后取均值）：

| 规模 | 网格 | 粒子 | GDScript 参照 | 原生 `PixelFluid` | 倍数 |
|---|---|---|---|---|---|
| 参照规模 | 17x18 | 130 | 1.134 ms/步 | **0.031 ms/步** | 36.5x |
| 血瓶量级 | 26x14 | 300 | 2.484 ms/步 | **0.068 ms/步** | 36.6x |
| ink-2 真实瓶身 | 60x59 | 4169 | 34 ms/步 | **1.087 ms/步** | 31x |

⚠️ 别只看原生那一列：参照实现 2.5 ms/步，一帧里塞几个瓶子就不行了。
它必须留着（逐位对拍的基准），所以扩展没加载时会**吵闹地**退回它。

### 接口

```gdscript
var f := FluidPBF.new()
f.resize_grid(nx, ny)            # 域 = nx*spacing x ny*spacing
f.solid_mask = mask              # 可通行掩码（x*num_y + y，x 主序）
f.init_particles(full)           # 密排六角晶格
f.set_fill_ratio(health)         # 液量跟着血量走
f.step(gx, gy)                   # 重力是**域单位**
var wet: bool = f.ink[x * f.num_y + y] != 0
```

⚠️⚠️ **原生持有权威状态**：`step` 只回吐 ink 掩码，读 `pos`/`vel` 之前必须
`sync_from_native()`。不同步会读到**初始状态**，而 ink 是当前的 ——
两个数对不上时人会先怀疑统计，不会怀疑探针（探针上真的踩过一次）。

⚠️⚠️ `fluid.ink` 是 **x 主序**（`x*num_y + y`），而 `PixelShape` 那套掩码是
**行主序** —— 同一个 `i` 查两边等于转置，症状是"一道斜杠贯穿瓶身"。

### 闸门

`tests/validation_fluid.gd` —— **38 项断言**。除了逐位对拍（pos/vel/ink/rest_density
200 步后完全相同），还有一条 `native_calls` 断言：**"这条路真的走过了"**。
没有它，重编失败时"原生 == 参照"会退化成 GDScript 跟自己比，报 36/36 全绿而原生
一个字节都没测到。

## 二、连通分量标注原生化（`PixelRaster` op 3）

### 为什么是它

CA / 游戏层最常问的两个问题 —— "这条线是哪一条""哪些体素属于同一个连通体" ——
底下都是 `Destruction.components()`（`ShapeOps.component_map()` 也是它）。
它是**纯位运算 + 数组**：块内是 uint64 迭代泛洪、接缝是 union-find、归组是拼装，
**没有任何 GDScript 特有的语义**。

### 性能

768x100 满实心（1152 块）：

| | GDScript 参照实现（**已开 WorkerThreadPool**）| 原生 |
|---|---|---|
| 一次全量标注 | 6.053 ms | **1.905 ms** |

⚠️ 参照实现那一列是**并行之后**的数字 —— 这 3.2 倍是**单线程 C++ 对多线程 GDScript**
拿到的，赢在每步没有函数调用开销（GDScript 一次调用 1289 ns、一次 Packed 下标写 23 ns）。

这也正面印证了 `src/gpu/gpu_destruction.gd` 文件头那句话：GPU 版内核本身只要 0.75 ms，
但周围的字典/数组记账 14.7 ms GPU 加不到 ——
**"真正的出路是把整条管线搬进 GDExtension，而不是只把泛洪搬上 GPU"**。现在搬的是整条管线
（块内泛洪 + 接缝 union-find + 归组 + 顺序）。

### 判据是逐位，不是"看起来一样"

同样的分组、同样的顺序、同样的掩码 —— **顺序不同也是不同**，它会原样进
Rapier 的碰撞体顺序。闸门 `tests/validation_components_native.gd`：
**49 项断言 / 23 个用例**（块内 32 分量的棋盘、满块、空块、缺块、负块坐标、
对角不算连通、12 组随机形状、768x100 满实心）。

同样钉了 `native_calls` 计数 —— 否则"悄悄退回 GDScript"会让逐位对拍变成同义反复。

### 接口

```gdscript
Destruction.components(shape)        # { 分量序号: { chunk_key: 掩码 } }，序号 0..n-1
ShapeOps.component_map(shape)        # { "count": n, "chunks": { key: PackedInt32Array(64) } }
```

## 升级注意

1. **要重新部署 addon**（原生 DLL 变了）。没部署不会算错，但会退回 GDScript 参照实现。
2. 重编 DLL 前**必须关掉编辑器**：DLL 被占用时 g++/Copy-Item 会**静默不产出**，
   而症状是"物理完全不动"（`tools/build_native.py` 为此主动中止并说明原因）。
3. 部署**只能走 `tools/deploy_engine_addon.ps1`**（或消费方自己的部署脚本），
   不要手工 `Copy-Item` —— 会把 `build_addon.py` 生成的 `.gdignore` 一起带过去，
   Godot 于是**整个忽略 addon**，症状指向完全无关的地方（`Nil.get_reference_count`）。
