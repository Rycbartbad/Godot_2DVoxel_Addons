# v0.3.7 —— 破坏性能（局部贴图 / 材质属性 / 局部连通）+ 冻结剔除 + 关节精度旋钮

## 一句话

**打一次洞不再是"整张重画"**：破坏的三个原语（`fracture` / `detach` / `fracture_pixels`）
改成只重建脏块，母体的质量/摩擦/恢复不再被打坏（游戏层那次 `refresh_mass()` 可以删了）；
新增**可逆的冻结/恢复**（相机剔除用，隐藏节点不会停物理这件事终于有解）；
关节的求解精度旋钮（软度 / 迭代次数 / warmstart）与约束误差诊断都能用了。

## 实测（768x100 底板 = 24 块，内部挖 20x20）

| 原语 | 改前 | 改后 |
|---|---|---|
| `fracture_pixels` | 24/24 块、~52 ms | **2/24 块、0.27 ms** |
| `detach` | 24/24 块、51.7 ms | **1/24 块、0.67 ms** |
| `fracture` | 1/24（本来就有 dmg_rect）| 1/24、0.19 ms |
| `detach` **贴边界小洞** | 23.13 ms | **7.51 ms（3.1x）** |

物理侧 A/B（200x200 内部挖 40x40，不含渲染同步）：`detach` **20.77 -> 12.77 ms**；
`fracture` 4.84 -> 5.20 ms（**+7% 是故意的代价**：它现在真的去算密度/摩擦/恢复了）。

## 新增 / 改动

| 接口 | 说明 |
|---|---|
| `PBody.rebuild(..., dirty_rects)` | 多接一个**按 shape** 的脏范围（一个矩形套给多 shape 不可能同时正确）|
| `PBody.internal_render` | `false` = 只做物理不渲染（**不要透明精灵占位**）|
| `PixelWorld.uses_internal_render(node)` | 渲染归属判据的唯一真源（`rebuild` / `bake_node` / `sync_world_bodies` / 每帧都走它）|
| `PWorld.freeze / unfreeze / freeze_component / joint_component` | **可逆**地关掉物理（单个 / 整组）|
| `PWorld.cull_freeze(rect, keep)` | 相机剔除：范围外冻结、范围内恢复；`keep` 的**整个关节组件**保持计算 |
| `PWorld.ccd_joint_aware` | **默认关**。焊接组当整体估子步（轻手挂重臂的瞬态不再顶全世界的子步数）|
| `PJoint.set_solver_softness(freq, damping)` | 关节求解软度（`<= 0` = 回 Rapier 默认）|
| `PWorld.rp_joint_solver_iterations / rp_warmstart_joints / rp_warmstart_coefficient` | 世界级求解参数（**不设就不推**，没调过的场景逐位不变）|
| `PJoint.anchor_error / angle_error / lateral_error` | 约束误差诊断（纯 GDScript，零原生调用）|

## 行为变化（要知情）

- **破坏之后母体的质量/摩擦/恢复不再被打坏。** 改前：`fracture` 母体 mass = 像素数、
  friction/restitution 被清成 0；`detach`/`fracture_pixels`/`ensure_connected` 清摩擦与恢复。
  ink-2 因此必须补一次 `refresh_mass()`（逐像素扫描 + 贪心分解 + 碰撞体重推 + 整张贴图重建
  再付一遍）—— **现在那次调用可以删了**。演示里"打过的石头变轻变滑"的手感会跟着变正常。
- `ShapeOps.attach_to` 那条路**仍然**没有世界引用（质量按像素数算）；摩擦/恢复已经不会被清 0。
- `ccd_joint_aware` 默认**关**（它拿掉了"瞬态速度"这道安全余量）。要用请先拿薄壁场景验过。
- `detach` 的"贴边界"早退以前**从来没生效**（判据在删除之后取），现在生效了 ——
  内部摘除不再白跑一趟全量连通分量标注。

## 怎么用

```gdscript
# ① 破坏：什么都不用改，贴图自动只重建脏块
# ② 材质属性：删掉破坏后的 refresh_mass() 调用
# ③ 相机剔除（区块外扩 2 格）
var r := Rect2(cam_topleft - Vector2.ONE * 2 * chunk, cam_size + Vector2.ONE * 4 * chunk)
px.cull_freeze(r, [player_body])      # 与玩家关节连接的整组不会被冻
# ④ 关节调精度：先量再调
j.anchor_error_len()                  # 漂了多少 px
j.set_solver_softness(8.0)            # 软一点（默认很硬）
```

⚠️ 三个世界级求解旋钮是"**显式设过才推**"；⚠️ `rp_joint_solver_iterations` **不是关节专属**
（Rapier 0.36 里它是整个求解的迭代次数，连无关节的落体都会被改）。

## 明确**没有**改的

- **表 ⑥（分片管线原生化）没有实现**：测量做完了（`tests/diag_split_profile.gd`），
  结论是瓶颈在"逐块的解释器 + 对象分配"，而批量化被**数据布局**卡住
  （破坏管线操作的是 GDScript 对象图，原生那侧看不见）—— 第一步是决定数据布局，
  不是写 op。详见 development_log。
- 表 ④（hand 的 CCD 步长 0.5 -> 2）在**游戏侧**，引擎不用改。

## 验收

- **8 条基准逐位不变**（重编两个 DLL 之后也专门核对过）；
- 闸门 **67 个脚本全绿**，其中本版新增：
  `validation_local_repaint`（12 项：只重建脏块 + **逐像素一致** + 形状对象没被换掉）、
  `validation_mass_after_destruction`（17 项：质量 = 剩余像素 x 密度、摩擦/恢复保持、
  体素守恒、冲量反推）、`validation_ccd_joint_aware`（12 项：含 2 像素薄墙防穿）、
  `validation_freeze`（19 项：含"解冻后质量在 Rapier 侧也对"的冲量反推）、
  `validation_joint_solver`（12 项：软度/迭代次数的实测方向 + 默认不推的契约）、
  `validation_node_render_policy`（18 项）、`validation_joint_error`（14 项）；
- 诊断：`diag_split_profile.gd`（分段耗时）、`diag_render_handoff.gd`（渲染交接）。
