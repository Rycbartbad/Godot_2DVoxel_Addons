# v0.3.2

从 v0.3.1 起共 11 个提交。这一版的主线是**把"拖动"这条路的帧时间压回可用范围**，
并修掉一处由优化本身引入的**碰撞体重叠**（它让分片的碰撞体成对重叠、数量多出 7 倍）。

## 拖动：8 帧 -> 200 帧量级

现象（甲方报的）：**1000 个矩形时，不拖动有 130 帧，一旦按住 Ctrl 左键拖动刚体，
哪怕没有接触到任何物体，都会掉到 8 帧。**

根因是两条叠加，都量过：

1. ccd 子步数按"最快**清醒**刚体每帧位移 / `ccd_max_motion(2.0)`"算 —— **与接触无关**，
   所以抓着东西**空挥也照样顶满**（实测一次快速拖动 = 25 子步）。
2. 子步是**全局**的：每个子步都要把整个世界步进一遍。实测每子步成本 ≈ **1 us/矩形**
   —— 1000 矩形时 25 子步 × 1 ms = 25 ms/帧；场景更重时就是 125 ms。

修法：**抓取时按世界大小压一遍子步数**（`ccd_grab_substep_cost_budget_us` / 总矩形数）。
它**只在抓取时生效**，不抓时完全走原来的行为，所以 8 条基准**逐位不变**。

| 状态 | 修复前 | 修复后 |
|---|---|---|
| 不抓、静止 | 1 子步 0.97 ms/帧 | 不变 |
| 抓着高速空挥 | 25 子步 **25.3 ms** | 5 子步 **4.56 ms** |
| 停下但不松手 | 26 子步 **23.3 ms** | 5 子步 **4.25 ms** |

> ⚠️ 代价写清楚：重场景 + 极端速度下每子步位移变大，被 `ccd_clamp_motion` 钳住 ->
> 那一帧**变慢动作**（绝不穿模，和子步上限被顶满时同一个取舍）。正常拖动速度
> （每帧几像素）根本碰不到这个上限，只有"甩"这种极端速度才会被钳。

## ⚠️ 修掉一处**优化本身引入的**碰撞体重叠

为了让分片复用母体的按块分解缓存，`_assemble` 里从分组自己推了一份块 key 列表，
而"发现新块"循环用 `sigs.has(bk)` 当判据 —— 两者叠加导致**同一个块被插两次**，
同一个块的矩形被 append 多次。

症状：768x100 一刀切开后，每片 **380 个矩形**、**每个像素被覆盖 2 次**（33198 处重叠）
= 分片碰撞体成对重叠、数量是应有的 **7 倍**。修好后每片 **53 个矩形**（覆盖逐像素精确）。

> ⚠️ 8 条基准**没抓到**它（它们不走 split），像素覆盖闸门也没抓到（它测的是独立形状，
> 不是分片）。所以新增 `tests/validation_fragment_cover.gd`：对**破坏 + 分裂之后**的每一片
> 逐像素比对 rects 与形状，phantom / missing / overlap 三个都必须为 0。

## 其它性能项（全部逐位等价或有闸门）

- **keep mask 判据按 kind 内联**（子表达式提升）：`apply_damage` 8.8 -> 6.5 ms，逐位等价
  （`validation_damage_mask` 12000 组对拍）。
- **质量属性用行/列 popcount 的边际量**（整块同材质时）：生成碎片 87 -> 52 ms；
  数值重排由 `validation_mass_props` 对**冻结的旧实现**守 1e-12。
- **整块拷贝走写时复制共享**：split 14.4 -> 13.5 ms，每片少 1098 次分配。
- **分片块 key 去重**：每片块 key 78 -> 12、矩形 380 -> 53、`decompose` 冷 6.5 -> 3.3 ms。

## ⚠️ 两条试过并撤回的路（别再走）

1. **挂钟时间预算**（给子步循环加"超时就少切"）：症状 25.6 -> 5.7 ms/帧 确实有效，
   但 `sleep_frag` 从 `-35.696264844083` 变成 `-35.400524684771`，**而且两次运行还不一致**
   —— 用挂钟做预算等于让物理依赖机器速度，基准与回放都不再可比。整段撤回。
2. **让子步迟滞"停下 0.25 秒后回落"**：症状也能压下去，但它拆掉了
   "拖动时子步数不回落"这条不变量（`test_physics` 的拖动用例当场抓到"回落 4 次"）——
   那是修"抓起别的物体时吊桥抽搐"的东西。
   **结论：该做的是给峰值设上限，不是让峰值掉下来。**
